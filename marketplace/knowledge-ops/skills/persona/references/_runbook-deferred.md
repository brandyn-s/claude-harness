- If saturation fails to reproduce → defaults are explicitly fixture-
  specific; update SKILL.md to label N=15 as "convenience default,

**The test**: a row in `~/Documents/knowledge-base/research/dispatch-runs/INDEX.md`

## P1 #6 — Replace bucket-coverage with axis-independence diversity metric

**Why it matters**: even with a perfect non-telegraphing fixture, M4's
N=11 saturation would still be tautologically guaranteed because saturation
is measured by *bucket coverage* on an inventory whose buckets were the
curator's organizing axis. Once each bucket is sampled, coverage is
mechanically guaranteed. Cross-fixture replication does NOT fix this.

**Spec**:
1. Add `scripts/diversity.py` with three diversity metrics:
   - **Recommendation embedding distance**: embed each persona's output,
     compute pairwise cosine, report mean and min pairwise distance.
     Voyage embeddings (we have VOYAGE_API_KEY).
   - **Judge-scored novelty distribution**: LLM-judge rates each
     recommendation against the others as "redundant" / "novel-but-
     overlapping" / "distinctive." Report fraction marked distinctive.
   - **Bucket-coverage** (existing): keep for comparison.
2. `analyze.py` reports all three metrics per run dir.
3. Define "saturation" as the N where the diversity metric stops
   increasing meaningfully — NOT the N where bucket coverage hits 100%.
4. M4 should be re-run on the synthetic fixture using the new metric;
   compare new saturation N against the old N=11. If new N > 11, the
   bucket-coverage saturation was indeed tautological.

**Effort**: ~200-300 lines of new code (diversity.py + analyze.py
update). API budget for re-running M4: ~$5.

**The test**: `scripts/diversity.py` produces all three metrics on an
existing run dir. Re-run of M4 reports the new saturation N alongside
the old. Methodology-evolution entry documents the comparison.

## P3 #11 — Context-bundle hybrid for closed-context dispatch

**Why it matters**: `dispatch_one()` calls `messages.create()` with no
`tools` parameter. Personas can only "read" what's hand-packed into the
`{problem}` string. The 2026-04-29 success story used Claude Code
sub-agents with full tool surface — different substrate. The closed-
context choice is intentional for rubric-mode reproducibility, but the
gap with the original dispatch is real and undocumented.

**Spec** (the "context-bundle middle path" surfaced in v1 cross-talk):
1. Add `scripts/build_context_bundle.py`. Given a problem description
   and optional hints (file globs, search terms), the script:
   - Runs Claude Code tool calls (Read, Grep, Glob) against the user's
     codebase or KB to gather relevant context
   - Archives the resulting bundle as a versioned blob in the run dir
   - Produces a deterministic context summary (1-2K tokens)
2. `dispatch.py` accepts `--context-bundle PATH`. When set, the bundle
   contents are embedded in `{problem}` before persona dispatch.
3. The bundle is git-committed alongside the run for reproducibility
   (rubric-mode pre-registration discipline applies).
4. Document the substrate difference explicitly in SKILL.md: personas
   operate on the packed `{problem}` plus the optional context bundle;
   they do NOT have repo inspection capabilities.

**Effort**: ~300-500 lines of new code. The bundle-builder is the bulk;
dispatch.py integration is a 50-line addition.

**The test**: A worked example run with `--context-bundle` produces
results comparable to a 2026-04-29-style sub-agent dispatch on the same
problem. Methodology-evolution entry documents the comparison.
