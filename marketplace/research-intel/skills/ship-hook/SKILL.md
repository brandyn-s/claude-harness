## ship-hook

# Ship Hook -- Install Staged Hook Specifications

Read a staged hook specification from `~/.claude/hooks/staged/`, write the
hook script, register it in `settings.json`, test it, and clean up the spec.

Staged specs are generated by `/distill` when it classifies a lesson as T0-hook.
This skill completes the second half: safe, atomic installation.

---

## Arguments

| Argument | What It Does |
|----------|-------------|
| *(none)* | List all staged specs in `hooks/staged/` and ask which to install |
| `{name}` | Install the named spec (matches `hooks/staged/{name}.spec.md`) |

---

## Step 1: Read the Spec

If no argument, list all `~/.claude/hooks/staged/*.spec.md` files. If none
exist, report "No staged hook specs. Run /distill to generate them." and stop.

If an argument is provided, read `~/.claude/hooks/staged/{name}.spec.md`.

The spec file contains:
- **Hook event** (spec may label this `Event`): PreToolUse or PostToolUse (required)
- **Matcher**: Tool name pattern (e.g., `Write|Edit`, `Bash`) (required)
- **Enforcement logic** (spec may label this `Logic`): Pseudocode or description of what to check (required)
- **Test case** (spec may label this `Test cases`): Known-bad input and expected outcome (block/fix) (required)
- **Behavior**: Fix silently, block with error, or advisory (optional; may be inferred from enforcement logic)
- **Timeout**: Recommended timeout in seconds (optional; default 3-8s)

**Validate the spec before proceeding to Step 2.** The required fields (`Hook event`/`Event`, `Matcher`, `Enforcement logic`/`Logic`, `Test case`/`Test cases`) must be present and non-empty under either label — the shorter synonyms are common in `/distill`-generated specs, and either spelling satisfies the gate. `Hook event` must be one of the event types this skill knows how to wire (`PreToolUse`, `PostToolUse`) — any other value (typo'd or unsupported event) gets reported with the invalid value named, and the run stops. The optional fields (`Behavior`, `Timeout`) may be defaulted if missing. If any required field is missing or malformed under both accepted labels, report the gap and stop — DO NOT write any files (hook script or settings.json) when the spec is incomplete. The user can fix the spec and re-run `/ship-hook`.

---

## Step 2: Check for Conflicts

Before writing anything:

1. **Name collision**: Check if `~/.claude/hooks/{name}.py` already exists.
   If so, read it. If the existing hook covers the same enforcement, report
   "Hook already exists at hooks/{name}.py — spec is redundant" and stop.
   If the existing hook is different, propose a different name.

2. **Duplicate enforcement**: Grep existing hooks for the same pattern/behavior.
   The consolidated hooks (`bash-security-guard.py`, `post-write-edit.py`) may
   already cover this case. If so, propose adding the new check to the existing
   consolidated hook instead of creating a new file.

3. **Matcher overlap**: Check `settings.json` for existing hooks on the same
   event + matcher combination. Multiple hooks on the same matcher are allowed
   but add latency. If the new hook's matcher overlaps with a consolidated hook,
   prefer adding to the existing hook.

Report findings. If a conflict exists, ask the user whether to proceed, merge
into existing hook, or abort.

**If the enforcement was already shipped elsewhere** (case 1 or 2 above
resolves to "already covered"), offer to delete the now-redundant spec file
from `hooks/staged/` in the same turn — don't just stop and leave it. A
confirmed-redundant spec that's never cleaned up is indistinguishable from
genuinely pending work on the next `/ship-hook` (argument-less) listing.
Live instance (2026-07-03): a `ps-process-listing-secret-leak-guard.spec.md`
staged 2026-06-20 sat unaddressed for 2 weeks after the exact enforcement it
proposed shipped directly into `bash-security-guard.py` the next day — same
recurrence count, same incident date, cited in that function's own
docstring. Only a manual audit caught it.

## Step 3: Write the Hook Script

Write `~/.claude/hooks/{name}.py` following the established pattern:

```python
"""Brief description of what this hook enforces.

Generated from staged spec: hooks/staged/{name}.spec.md
Installed by /ship-hook on YYYY-MM-DD.
"""

import json
import sys

def main():
    try:
        data = json.loads(sys.stdin.read())
        tool_name = data.get("tool_name", "")
        tool_input = data.get("tool_input", {})

        # Enforcement logic from spec
        # ...

        # ALLOW: exit 0, no output
        sys.exit(0)

    except Exception:
        # Never crash — allow on error
        sys.exit(0)

if __name__ == "__main__":
    main()
```

**Requirements:**
- Read JSON from stdin, extract `tool_name` and `tool_input`
- Wrap all logic in try/except — an uncaught exception exits 1, which Claude Code treats as a NON-blocking error (only `exit 2` blocks the tool call); a crash won't stop the call but it surfaces a `hook error` notice and, for auto-fix hooks, silently loses the `updated_input`
- Use portable exec form: direct `run-hook` on POSIX/WSL; on native Windows,
  use Git for Windows `bash.exe` with `run-hook` as the first argument
- For blocks: `print(message, file=sys.stderr); sys.exit(2)`
- For auto-fixes: `print(json.dumps({"decision": "approve", "updated_input": {...}})); sys.exit(0)`
- For advisory: `print(message, file=sys.stderr); sys.exit(0)`

## Step 4: Register in settings.json

**Use the architecture's tested registrar. Do not open-code another
read-modify-write implementation.** The registrar serializes cooperating
processes, refuses a non-cooperating concurrent edit, preserves supported file
metadata, deduplicates by event + matcher + hook identity, reconciles timeout
and exec form, validates Git Bash on native Windows, and raises the Claude Code
minimum-version floor.

```bash
CONFIG_ROOT="${CLAUDE_CONFIG_DIR:-${HOME:?HOME or CLAUDE_CONFIG_DIR is required}/.claude}"
REGISTRAR="${CLAUDE_PLUGIN_ROOT}/scripts/wire_hooks.py"

# A marketplace installation carries the same tested registrar. Its dispatcher
# must be copied into the user config before registering a user-owned hook.
if [ ! -f "$REGISTRAR" ] && [ -n "${CLAUDE_PLUGIN_ROOT:-}" ]; then
  REGISTRAR="$CLAUDE_PLUGIN_ROOT/scripts/wire_hooks.py"
fi
if [ ! -f "$CONFIG_ROOT/hooks/run-hook" ] && [ -n "${CLAUDE_PLUGIN_ROOT:-}" ]; then
  cp "$CLAUDE_PLUGIN_ROOT/hooks/run-hook" "$CONFIG_ROOT/hooks/run-hook"
  chmod +x "$CONFIG_ROOT/hooks/run-hook"
fi

test -f "$REGISTRAR"
test -x "$CONFIG_ROOT/hooks/run-hook"
PYTHON_BIN="$(command -v python3 || command -v python)"
"$PYTHON_BIN" "$REGISTRAR" "$CONFIG_ROOT/settings.json" \
  "{EVENT}|{MATCHER}|{name}.py|{TIMEOUT}"
```

Treat any registrar error as a failed installation. Do not fall back to direct
JSON editing. On native Windows, set `CLAUDE_CODE_GIT_BASH_PATH` to Git for
Windows' real `bash.exe` if automatic discovery cannot validate it.

**If adding to an existing consolidated hook** (Step 2 found overlap), skip
this step — the registration already exists. Instead, edit the existing hook
script to add the new enforcement logic.

---

## Step 5: Test

Execute the test case from the spec:

1. Create a throwaway file or command that triggers the known-bad pattern
2. Simulate a tool call by piping the expected stdin JSON to the hook script:
   ```bash
   echo '{"tool_name": "Write", "tool_input": {"file_path": "'"${TMPDIR:-/tmp}"'/test.md", "content": "bad pattern"}}' | python3 ~/.claude/hooks/{name}.py
   ```
3. Verify: exit code matches expected (2 for block, 0 for allow/fix)
4. Verify: stderr or stdout output matches expected behavior
5. Clean up throwaway files

If the test fails, report the failure and DO NOT delete the spec. The user
can re-run `/ship-hook` after fixing.

---

## Step 6: Clean Up and Report

If the test passed:

1. Delete the spec file: `rm ~/.claude/hooks/staged/{name}.spec.md`
2. **Record the install in `bin/staged-spec-staleness.py`'s `MARKERS` entry for this
   spec** — set `shipped_by` to the PR number, date, and marker, and confirm the
   marker string you shipped actually appears in the target file:

   ```bash
   python3 bin/staged-spec-staleness.py     # must NOT report this spec as unverifiable
   ```

   If you installed the fix somewhere other than the spec's declared target, repoint
   `target` too. A marker left pointing at the wrong file reports `live` forever, so a
   later session re-derives work that already shipped — which is the incident that
   tool exists for.
3. If `hooks/staged/` is now empty, leave it — it's the staging directory
   for future specs.
4. **Before deleting anything, grep for references to the spec path.** Test files hold
   path constants to staged specs: measured 2026-08-27, `git rm` on two shipped specs
   broke `test_zsh_dialect_guard.py`, which had `WORD_SPLIT_SPEC` / `GLOB_SPEC`
   constants pointing at them. The staleness tool prints `ACTION: git rm <spec>` and
   does not check for consumers, so this step is yours:

   ```bash
   grep -rn "{name}" --include='*.py' --include='*.md' --include='*.yaml' .
   ```

Report:

```
HOOK INSTALLED

  Script:   hooks/{name}.py
  Event:    {PreToolUse|PostToolUse}
  Matcher:  {matcher pattern}
  Behavior: {block|fix|advisory}
  Timeout:  {N}s
  Test:     PASSED
  Spec:     DELETED (installed successfully)

  Note: Hook is active in NEW sessions. Current session uses
  cached settings.json — restart to pick up the new hook.
```

---

## Success Criteria

- Spec file is read and validated before any writes
- Conflict check catches duplicate enforcement in existing hooks
- Hook script follows the established pattern (stdin JSON, try/except, correct exit codes)
- Registration uses Python read-modify-write with atomic rename via `os.replace` (not Edit tool, not bare `write_text`)
- Test case from spec is executed and passes before cleanup
- Spec file deleted only after successful test
- Report includes the "new sessions" caveat about settings.json caching

## Examples

**Example 1: Install a staged spec**

User says: `/ship-hook staged-additions-guard`

Actions:
1. Read `hooks/staged/<name>.spec.md` — here, the staged-additions-guard spec
2. No conflicts — no existing hook covers staged-additions guarding
3. Write `hooks/staged-additions-guard.py` (PreToolUse on Bash, blocks `git commit` when the working tree has unintended staged additions)
4. Register in settings.json under PreToolUse with matcher `Bash`
5. Test: stage an unintended file, attempt `git commit`, verify the hook blocks it
6. Delete spec, report success

**Example 2: List all staged specs**

User says: `/ship-hook`

Actions:
1. List `hooks/staged/*.spec.md`: 2 files found
2. Present: "2 staged hook specs: md-table-spacing, encoding-check. Which to install?"

**Example 3: Spec conflicts with existing hook**

User says: `/ship-hook encoding-check`

Actions:
1. Read spec — PreToolUse on Bash, checks Python commands for missing encoding='utf-8'
2. Conflict: `bash-security-guard.py` already has a PreToolUse:Bash matcher
3. Report: "bash-security-guard.py already handles PreToolUse:Bash. Recommend adding this check to the existing hook instead of creating a new file. Proceed with merge, or create separate hook?"
